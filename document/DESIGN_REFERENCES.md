# 分模块设计参考与逻辑取舍

日期：2026 年 10 月 2 日。

状态：基于官方仓库、源码与文档的研究及设计建议。没有安装、运行、部署或引入以下项目代码，尚未确定组件选型。产品要求和验收以 [PRD](PRD.md) 及 [课程支持矩阵](COURSE_SUPPORT.md) 为准。

## 1 研究方式

按课程活动、任务核验、代码执行、实验、协作恢复和复习分别研究机制，避免把一个项目的完整产品结构直接作为我们的需求。来源仅使用项目官方仓库和文档，核查日期如上；实际采用代码时再锁定提交、版本与许可证。

以下“可借鉴”是本项目的设计建议，“源码或文档体现”是参考项目的能力，两者不能混写。当前许可证仅用于选型比较，不表示已经完成未来依赖的许可核对。

### 2.1 课程活动与题目

Docling 可参考 PDF、DOCX 等材料转换与统一文档结构，用于保留标题、表格、公式和代码等课程内容。我们应将材料版本、章节、知识单元与具体出处关联，展示解析缺失和待校核内容；抽取到的相关概念不自动成为先修关系或学生能力结论。[官方项目](https://github.com/docling-project/docling)、[文档数据结构](https://docling-project.github.io/docling/concepts/docling_document/)

Moodle 提供活动完成规则与能力记录，可参考其分层组织方式。穹隆应允许学生自己建立课程和开始学习，教师维护内容、标准与审核，不成为自主启动的前置条件。看过材料、完成活动与独立掌握仍需区分。[活动完成](https://docs.moodle.org/501/en/Activity_completion)、[能力与证据](https://docs.moodle.org/501/en/Competencies)

PrairieLearn 的题目生命周期和外部评分接口，适合参考任务生成、提交解析与核验分离；其工作区机制还提示我们区分编辑状态与正式提交。用于数学、数据库或 AI 的具体检查器，需要我们根据任务另行设计。[题目生命周期](https://docs.prairielearn.com/question/server/)、[外部评分](https://docs.prairielearn.com/externalGrading/)、[工作区](https://docs.prairielearn.com/workspaces/)

### 2.2 执行与判题

Judge0 的 API 可参考提交、查询与结果结构，但其源码在没有预期输出时也可能把正常运行标为 Accepted。因此接入执行器时，不能直接把供应端的成功状态映射为学生答案正确。[API](https://ce.judge0.com/)、[状态判定源码](https://github.com/judge0/judge0/blob/master/app/jobs/isolate_job.rb#L323)

Piston 可参考运行时版本与编译／运行阶段结果。其执行输出本身不是题目判定；进程内等待队列也不能替代我们所需的持久任务与恢复。其官方公共 API 自 2026 年 2 月 15 日起需要授权，并面向特定非商业教育用途，因此产品不预设依赖免费公共 API；候选部署方式需在架构阶段比较。[官方项目与 API 条件](https://github.com/engineer-man/piston)、[执行任务源码](https://github.com/engineer-man/piston/blob/master/api/src/job.js#L84)

DOMjudge 可参考多个测试点、比较器、判题记录与重新判题。学习反馈应告诉学生实际失败条件和后续可做什么，不能只保留竞赛式总结果。[判题流程](https://github.com/DOMjudge/domjudge/blob/main/doc/manual/judging.rst)

SQL 另配隔离数据库和结果比较；Web 服务、系统和网络实验另配受控适配器。通用编译器支持一种语言，不意味着已经覆盖所有用该语言完成的实验。

### 2.3 实验文档、协作和复习

JupyterLab 可参考实验文档的组织。为了获得可复核证据，应保存代码、数据和依赖版本，在干净内核中重新运行，避免旧输出和隐藏执行顺序造成误判。它本身不替我们提供评分器或代码隔离。[Notebook](https://jupyterlab.readthedocs.io/en/stable/user/notebook.html)、[内核管理](https://jupyterlab.readthedocs.io/en/stable/user/running.html)

LangGraph 将当前会话检查点与跨会话存储区分，并支持等待用户输入后恢复。中断所在节点恢复时可能重新执行，因此提交和状态更新需要幂等；内存检查点也不能满足服务重启后的恢复要求。框架不能代替课程、证据、权限和学习判断模型。[持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[中断语义](https://docs.langchain.com/oss/python/langgraph/interrupts)

py-fsrs 可参考记忆性内容的复习日志与排程。其卡片回忆状态不等于编程、推理或整门课的掌握；无真实历史时，不声称已完成个人参数拟合。复习算法是后续扩展，初版仍可基于实际单元和人工可解释规则安排再次核验。[调度和持久化接口](https://github.com/open-spaced-repetition/py-fsrs)

## 3 对本项目的设计建议

### 3.1 统一活动与证据，适配不同课程

课程 → 单元 → 能力目标 → 活动／任务 → 学生产物 → 工具或标准核验 → 证据 → 下一步。

活动至少区分概念学习、推理与证明、代码实践、SQL、数据实验和设计产物。各自使用适合的核验方式，共享目标确认、帮助记录、版本、进度与恢复机制。这样常见课程可以进入同一学习空间，不必为每门课另写一套产品。

教师维护课程模板、资料出处、任务和标准。学生有自己的路线、尝试与证据，能够自主开始或修改范围。内容模板和个人状态分开，修订内容不覆盖历史作品。

### 3.2 三层运行与核验

1. 执行层：根据允许的语言和环境执行学生代码，返回真实编译／运行事实。
2. 核验层：用已核对的测试、比较器或评价标准检查产物，返回维度、依据与限制。
3. 学习层：结合任务目的、提供的帮助、解释与新变体表现，提出状态判断及后续建议。

三个层次各自拥有状态。没有核验依据时只报告运行情况；环境错误不会扣成知识错误；核验通过也不会直接写成长期掌握。具体比较规则与支持清单在任务和环境版本中记录。

### 3.3 统一执行任务契约草案

本节用于后续 API 和数据设计，不绑定上述执行器的字段或状态名称。

| 类别 | 需要保存的信息 |
|---|---|
| 归属 | 学生、课程、任务和尝试 ID，权限与幂等键 |
| 产物 | 源码或作品版本，允许的文件结构，输入 |
| 环境 | 语言、编译器／解释器版本、镜像或环境版本、依赖和资源配置 |
| 执行 | 排队及运行时间、编译输出、标准输出和错误、退出码或信号、截断及资源状态 |
| 核验 | 测试集和检查器版本、每个测试点结果、失败原因与适用条件 |
| 恢复 | 当前状态、取消、重试关系及迟到结果处理 |

源代码编辑、执行与正式核验分别留痕。异步任务由持久队列或等效机制管理；沙箱生命周期、取消和清理需要后续实际验证，不能只从参考项目说明推断安全或稳定。

### 3.4 多 Agent 的交接与等待

协调角色读取当前目标与活动，按需请求诊断、辅导、任务或核验职责。交接包包含同一版本的作品、工具结果、帮助记录、证据 ID、缺失信息和预期输出，避免各角色用自己的摘要覆盖事实。

提出目标草案后等待本人确认；给提示后等待尝试或解释；提交后等待实际核验；失败则恢复到修改与重试。状态更新由明确规则和数据服务控制，角色不能根据对话自行跳过学生操作或核验。

角色数量和运行框架后置选择。先在一个真实学习流程验证必要协作，再扩展职责，观察学习价值、等待时间和成本。

### 3.5 持续学习与复习

当前会话保存具体任务和等待位置；长期记录保存版本化的目标、作品、帮助和核验事实。返回后先恢复这些信息，再生成建议。复习任务针对证据中的待验证或需再次应用部分，不用签到、消息轮数或卡片回忆率概括课程能力。

### 3.6 网络实操与过程证据

基础网络实验使用真实受控节点，通过网页提供拓扑、终端和报文查看。研究底座与检查器、终端回放和状态快照的组合，按任务保存操作与核验结果；厂商专有环境作为独立适配类型。对应官方资料和设计边界见 [网络实验工作台设计](NETWORK_LAB_DESIGN.md)。

## 5 设计和实现顺序

先确定课程与活动的数据关系、学生操作和完成条件；随后设计多语言执行与各类核验适配器，并实现持久进度与必要 Agent 交接。用个人真实学习发现问题，同时用课程和语言矩阵验收支持范围。

基础网络实验已补入第一阶段方案；Notebook 工作区、更复杂的系统／网络实验和复习算法按实际需求继续扩展。选型时比较可部署性、版本与依赖、隔离、持久恢复、维护成本和许可条件，不以仓库名称或展示效果代替可运行验证。
