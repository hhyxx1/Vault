## A：温度为什么一直是零

给定 `f = 50`，用 `double c = (f - 32) * (5 / 9);` 换算温度，按 `%.2f` 输出。先分别预测括号中的商、乘积和显示文本，再运行。任务期望为 `10.00`；初始作品输出 `0.00`，正常结束不等于任务正确。

修改除法的操作数后重试。比较 `5 / 9` 和 `5.0 / 9.0`，解释为什么只把接收变量声明为 `double` 不能恢复已经丢失的部分。提示分两层：先检查中间表达式的类型，再检查发生转换的时刻。参考修改只在自主查看后展示，不替换学生作品。

新条件采用 `-7 / 3` 和 `-7 % 3`，预测两个结果，再核对重建式 `商 * 除数 + 余数`。需要解释向零截断，不能套用向负无穷取整。随后将华氏温度改为 32、68 和负值，分别记录预测、观察和修改理由。这里的显示精度不是任意浮点值精确表示的证明。

## B：金额的单位先于变量名字

商品单价 199 分、数量 3，任务期望显示 `5.97`。初始作品先做 `199 / 100` 再乘数量，学生先解释每一步的单位，观察丢失的小数部分。修正作品用整数保存分，在显示时分出元和两位分；固定小范围避免整数乘法越界。要求写出当前允许的单价、数量范围，不能泛称“整数金额不会溢出”。

新条件：总价 597 分打九折，业务规则明确为计算后舍去不足一分的部分，因此应收 537 分。学生区分该业务规则与四舍五入，提出一种规则改变后原程序会不适用的例子。负金额、税率、任意大账单和通用货币规则不在这次受控任务中。

## C：安全地观察转换与边界

先比较 `(int)3.9` 和 `(int)-3.9`。两个输入在可表示范围内；这不是对任意浮点输入都安全的保证。

提供使用 `<limits.h>` 的边界防护程序：值为 `INT_MAX` 时拒绝加一，否则才执行加一。学生解释为何检查放在运算之前，并把输入改为 `INT_MAX - 1` 重试。不运行有符号溢出程序来采集一个“正确答案”，也不把本机 int 位数写成 C 的普遍规则。
