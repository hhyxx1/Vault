## A：先预测一次失败，再让程序运行

将下列文件保存为 `main.c`，选择 C17，不提供标准输入。先判断失败会发生在编译还是执行阶段，再运行。

```c
#include <stdio.h>
int main(void) {
    puts("Hello, learner!")
    return 0;
}
```

第一次观察只检查：编译阶段是否失败、错误日志指向哪里。不要把某一行英文诊断作为固定答案，编译器诊断文字可能变化。只改一处，再运行，比较两个不可变作品版本。修复后应输出 `Hello, learner!` 加一个换行。随后把字符串改为自己的学习目标，再运行，解释哪些内容是源文件、哪些是实际输出。

理论在失败后按需展开：GCC 的处理可以经过预处理、编译、汇编和链接；构建完成后才有本次可执行程序。`puts` 输出字符串并补换行。具体执行环境仍以本次运行记录为准。

分层提示：先看诊断附近的语句；再比较其他语句结尾；最后按需显示补分号的参考修改。查看答案可自主选择，记录与本次尝试绑定。

## B：运行成功为什么仍可能错

任务要求输出 `5` 和换行。初始程序使用 `puts("23");`，保留 `return 0;`。先运行，再判断“编译通过、退出正常”和“满足任务”是否是同一个条件。将输出改为 `5` 可以满足这一固定输入任务，但不能证明已经会处理任意输入。

另一个变体将 `return 0;` 改为 `return 3;`：它可能已经写出预期文本，随后以非零状态结束。平台会将这种结果显示为程序运行出错；这属于平台的工具分类，不证明发生了非法内存访问，也不代表输出自动正确。

不要用除以零、未初始化读取或格式串类型错配制造“固定的运行结果”；这些例子涉及未定义行为，不适合作为本模块的可重复答案。

## C：改变输入，并解释每条通道

下一活动采用有限输入协议：只检查首个 ASCII 字符是否为 `A`，后续字符在本活动中忽略；读取失败或首字符不是 `A` 则给出错误输出并非零结束。初始代码与输入需单独冻结，标准输入分别用 `A`、`B` 和空输入。这里不要求通用整数解析，避免把溢出等后续内容混进首课。

```c
#include <stdio.h>
int main(void) {
    int ch = getchar();
    if (ch != 'A') {
        fputs("expected A\n", stderr);
        return 3;
    }
    puts("accepted");
    return 0;
}
```

学生填写三次运行的标准输出、错误输出、退出状态预测，再对照真实结果；解释“空输入已经结束”和“在交互终端继续等待”之间的差异。执行服务的输入是提交时已经确定的有限流，并非交互式终端。
